UNO R4 WiFi bridge firmware: Arduino's 0.6.0 plus **UDP push mode**.
With push mode on, the bridge sends each received UDP datagram to the
RA4M1 by itself, so the RA4M1 can sleep until its UART receive
interrupt fires instead of polling. Push mode is opt-in: a sketch that
never asks for it sees Arduino's stock 0.6.0 behavior.

> [!IMPORTANT]
> This is **not an Arduino release.** It is a fork of Arduino's 0.6.0
> bridge, built from this tag. To go back to stock, use the
> [`v0.6.0-stock`](https://github.com/TonyMarkham/unor4-wifi-interrupt-bridge/releases/tag/v0.6.0-stock)
> release (see "Going back to stock" below).

## What push mode does

One new AT command, sent by the RA4M1 for a UDP socket it has opened
with `AT+UDPBEGIN`:

```
AT+UDPPUSH=<sock>,<0|1>
```

`1` turns push mode on for that socket, `0` turns it off. The reply is
`+UDPPUSH: ` and `OK`, or `ERROR` for a socket that does not exist.

While it is on, every datagram received on that socket is sent to the
RA4M1 unasked, as one frame:

```
+UDPRX: <sock>,<len>|<len bytes>\r\n
```

No `OK` follows a frame; it is not a reply to anything.

Rules for the RA4M1 side:

- A `+UDPRX:` frame can arrive between any two replies, including
  between a command and its reply. Parse it as its own frame.
- Do not send `AT+UDPPARSE` or `AT+UDPREAD` for a socket in push mode;
  the bridge is already reading its datagrams.
- Push mode is off for every new socket, and `AT+UDPSTOP` and
  `AT+SOFTRESETWIFI` turn it off. It survives a reset of the RA4M1
  (that does not reset the bridge), so a sketch should send
  `AT+SOFTRESETWIFI` at startup. Arduino's `WiFiS3` library already
  does this.
- Keep the traffic under the AT link's speed (115200 baud, about
  11 kB/s including frame headers). If the bridge's 16 KB output queue
  fills up, it drops its oldest data, which can cut a frame.
- Empty (zero-byte) datagrams are not forwarded.

## How to tell this firmware from stock

| Where | Stock 0.6.0 | This release |
|---|---|---|
| `AT+UDPPUSH=…` | `ERROR` | `OK` |
| `AT+FWVERSION?` | `0.6.0` | `0.6.101` |
| USB product name (`lsusb -v`) | `UNO WiFi R4 CMSIS-DAP` | `UNO WiFi R4 CMSIS-DAP (interrupt)` |
| USB `bcdDevice` | `0.06` | `0.06` (unchanged) |

The version keeps Arduino's `0.6` and uses patch number `101`
(100 + fork revision 1), so it always reads as "based on Arduino 0.6".
The HID version report and `AT+FWVERSION_U32` carry the same `101`.

## Other changes

- **Upstream bug fix:** when `AT+UDPBEGIN` or `AT+UDPBEGINMULTI` failed,
  the bridge freed the socket but kept a pointer to it, so later
  commands on that socket number used freed memory. The slot is now
  cleared.

Nothing else differs from Arduino's 0.6.0. `WiFiS3` on the RA4M1 works
unchanged: it only reports the bridge version and does not act on it.

## Example code

[`examples/UDPPushSleep`](https://github.com/TonyMarkham/unor4-wifi-interrupt-bridge/tree/v0.6.0-interrupt.1/examples/UDPPushSleep)
is an Arduino sketch for the RA4M1 that uses push mode the way it is
meant to be used:

- it joins WiFi with `WiFiS3`, then sends `AT+FWVERSION?`,
  `AT+UDPBEGIN` and `AT+UDPPUSH` itself over the AT link;
- it **sleeps** (`__WFI()`) whenever there is nothing to read, so only
  an interrupt wakes it — the UART receiving a frame from the bridge;
- it parses each `+UDPRX:` frame (socket, length, payload) and prints
  the payload, together with how many times it woke up with nothing to
  read since the previous datagram.

To make the sleep real, it stops the Arduino core's 1 ms `millis()`
timer after setup, so `millis()` and `delay()` stand still afterwards.
It checks for data and goes to sleep with interrupts masked, so a byte
arriving in between cannot be missed. Its source comments explain each
part.

## How it was built and tested

Built from this tag (`v0.6.0-interrupt.1`) with
[`docs/build-interrupt-procedure.md`](https://github.com/TonyMarkham/unor4-wifi-interrupt-bridge/blob/v0.6.0-interrupt.1/docs/build-interrupt-procedure.md),
using the same toolchain as `v0.6.0-stock` (ESP32 platform 2.0.9,
GCC 8.4.0, arduino-cli 1.5.1, esptool 4.5.1, espflash 2.0.0, Ubuntu
26.04). Two separate builds produced this file byte for byte.

Tested with
[`docs/flash-interrupt-procedure.md`](https://github.com/TonyMarkham/unor4-wifi-interrupt-bridge/blob/v0.6.0-interrupt.1/docs/flash-interrupt-procedure.md)
on a UNO R4 WiFi: the board starts and shows the new USB name, accepts
a sketch upload, joins WiFi, and reports `0.6.101`. With
`examples/UDPPushSleep` on the RA4M1, six datagrams sent from a PC at
different intervals each woke the sleeping RA4M1 as a `+UDPRX:` frame,
with **0** wake-ups in between.

## How to flash it

Follow
[`docs/flash-interrupt-procedure.md`](https://github.com/TonyMarkham/unor4-wifi-interrupt-bridge/blob/v0.6.0-interrupt.1/docs/flash-interrupt-procedure.md),
steps 1–4. It assumes you have already followed
`docs/build-original-procedure.md` once on your computer, for the
tools and the serial-port access. Then step 5 tests push mode.

The only difference from the procedure: instead of building the image,
check the download. In the folder that holds both files:

```
sha256sum -c SHA256SUMS
```

It must print `UNOR4-WIFI-S3-0.6.0-interrupt.1.bin: OK`. If it prints
anything else, do not flash the file. Then, in step 4.1, use the path
of the file you downloaded.

> [!WARNING]
> Flash this file only at address `0x0`, with espflash 2.0.0, exactly as
> step 4.1 shows. Do not use the esptool command in Arduino's README:
> its offsets do not match this board's partition layout.

## Going back to stock

Flash the `v0.6.0-stock` image the same way; the flash procedure's
"Going back to stock" section has the exact steps, including the
download and its checksum.
